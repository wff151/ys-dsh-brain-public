# V2 预注册：H-协作（格式协议在多 agent 传递中是否降低协调成本）

状态：冻结（2026-10-01）。本文档是 V2 判据权威；run-v2.mjs 的任务定义与
判定逻辑必须与本文一致，改动需同步两处。任何跑后修改须记录理由、可审计。

---

## 0. 核心假设与陷阱警示（用户 2026-10-01 拍板）

**H-协作**：格式协议（黑板/resume/折叠）在多 agent 传递中是否降低协调成本。

**陷阱（必须避开）**：单比"有黑板 vs 没黑板"测到的是**信息量**，不是**协议**。
多拿到一份 issues 当然决策更好——这是信息量增益，V0/V1 已反复证明"给信息就有增益"。
要测协议本身，必须用 P/N/F 三组控制信息量。

## 1. P/N/F 三组定义（信息通道对照）

所有组共享**同一个阶段 1**（temperature=0 可复现，阶段 1 只跑一次、三组共用）。

| 组 | 阶段 2 拿到什么 | 传输方式 | 用途 |
|---|---|---|---|
| **P（协议组）** | prevSummary + 通过黑板取回 issues（resume/search） | 模型输出 memory_reads 声明 → 脚本代读真实 store → 取回内容注入第二轮 | 主测 |
| **N（无信息组）** | 只有 prevSummary（无 issues、无读取提示） | 无 | 下界 |
| **F（有信息无协议组）** | prevSummary + **阶段 1 issues 全文直接注入** | 上下文注入 | 上界 |

**P 组取回协议（写死）**：
1. 阶段 2 第一轮 user 消息 = prevSummary + stage2 题面 + P_TAIL（要求：如需上一阶段
   记录，输出 memory_reads 声明，格式 `{"memory_reads":[{"tool":"resume|search","query":"string"}]}`）。
2. 模型输出合法 memory_reads → 脚本代读：`resume` → portable readResume(sessionId)；
   `search` → public listAllPublicMemories 按 query 匹配（title/tags/unresolved 包含）。
   取回结果拼接为阶段 2 第二轮 user 消息（前缀"上一阶段记录取回结果："）。
3. 模型输出决策（本轮不再解析 memory_reads）。
4. memory_reads 缺失/格式非法 → 该 trace 记为"P 组未发起取回"，传递完整性=0，不重试。

## 2. 判读规则（预注册，跑后不变）

- **P > N**（决策质量 P 高于 N）→ 有 issues 信息有增益（信息量价值，预期存在，不意外）。
- **P ≈ F**（决策质量差 ≤1 档）→ 黑板取回与直接给等价 → **协议价值 = 信息传递完整性**（协议本身无额外增益，V1 同型负结果）。
- **P < F** → 黑板取回有损（折叠丢失/截断/取回失败）→ 协议价值为负。
- **P > F** → 结构化 issues 让 agent 比"直接看全文"更好用 → **真协议增益**（极罕见）。

## 3. 三拆指标（替代"看最终答案"，分别报，不混成一个分数）

1. **传递完整性**（P 组）：取回内容命中 key_facts ÷ key_facts 总数。≥80% = 完整传递。
2. **使用效率**（P/F 组）：阶段 2 决策输出命中 key_facts ÷ key_facts 总数。
3. **决策质量**（P/N/F 三组）：阶段 2 决策方向与 expected_decision 一致（两档：一致/不一致）。
   判定标准：决策方向 + 理由中出现 key_facts 支撑 = 一致；方向对但无 key_facts 支撑 = 一致（弱）；
   方向错 = 不一致。P vs N vs F 三组对比。

## 4. 任务设计原则（沿用 V1 教训，写死）

1. **题面只给事实和约束，不给结论或建议方向**。凡判据要求的推理结果，题面不得出现。
2. **key_facts 只在阶段 1 题面出现**，阶段 2 题面不得重复——否则 P/N/F 无区分。
3. **expected_decision 依赖 key_facts**：删掉 key_facts，expected_decision 无法导出。
   （出题者预期 ≠ 判据；预期只用于任务自检与判定参考，模型给出合理替代方案按"一致（弱）"记。）
4. 简单任务不启用；每任务内建"交接"需求——阶段 2 决策必需阶段 1 的关键变量。

## 5. 任务集（6 任务 × P/N/F = 18 trace）

### T1 支付扩容（关键变量：功能范围与容量）
- **stage1**：团队 3 人，2 周后需上线支付功能。业务要求功能完整（主扫、被扫、退款、对账）。
  技术评估：完整实现需 4 周；简化版（仅主扫 + 自动对账）2 周可上线。分析主要矛盾，
  列出关键变量（功能范围、期限、人力、工作量），写入 issues。
- **key_facts**：`简化版`、`2周`、`4周`、`3人`
- **stage2**：新情况：上线后日均交易量预估从 1 万笔增至 50 万笔，支付成功率要求 99.5%，
  2 周上线期限不变。给出决策与理由。
- **expected_decision**：需调整方案——简化版功能集在 50 万笔下容量不足，扩功能或加人/
  调整上线策略，不能维持"原简化版 + 原样上线"。关键依据：简化版功能集（stage1 key）。

### T2 定价（关键变量：价格敏感阈值）
- **stage1**：新品类定价。市场调研显示用户价格敏感，定价高于现价 140% 将流失主要用户群。
  候选：高价策略（定价现价 200%，利润率 40%）vs 低价策略（定价现价 120%，用户接受度高）。
  分析主要矛盾，列出关键变量，写入 issues。
- **key_facts**：`200%`、`40%`、`120%`、`140%`
- **stage2**：监管新规：该品类价格上限为现价的 150%（硬性）。公司财务部门要求该品类
  利润率不低于 35%（对应定价不低于现价 145%）。给出定价决策与理由。
- **expected_decision**：需识别区间互斥（≤150% 监管 / ≥145% 财务 / ≤140% 增长 无交集），
  给三方权衡方案（如放弃财务 145% 或协商监管），不能只选"150% 兼顾"。关键依据：
  140% 敏感阈值（stage1 key）。

### T4 技术选型（关键变量：自研/采购周期与质量）
- **stage1**：预算充足。为订单系统选技术方案：自研（质量高、周期 6 周）vs 采购现成方案
  （质量中、周期 2 周）。分析主要矛盾，列出关键变量，写入 issues。
- **key_facts**：`自研`、`6周`、`采购`、`2周`
- **stage2**：预算削减 25%。自研方案周期不变（6 周）；采购方案需重新询价评估（价格可能
  上调）。给出决策与理由。
- **expected_decision**：需重评估，不能维持原决策（预算变化改变自研/采购权衡；采购成本
  未确认需重评，可能转向采购或缩自研范围）。关键依据：自研 6 周/采购 2 周（stage1 key）。

### T5 数据迁移（关键变量：迁移期限与库规模）
- **stage1**：一周内将旧库（MySQL 5.7，4TB）迁移至新库（MySQL 8.0）。分析主要矛盾，
  列出关键变量，写入 issues。
- **key_facts**：`一周`、`4TB`、`MySQL 5.7`、`MySQL 8.0`
- **stage2**：运维反馈：旧库部分表存在重复订单号、空字段；备份周期为每周一次，上周备份
  因磁盘满失败，最近一次完整备份为 3 周前。给出迁移方案与理由。
- **expected_decision**：先解决数据完整性与备份（不能直接全量迁移），并评估"补备份 +
  迁移"是否在一周内可行。关键依据：一周期限 + 4TB（stage1 key）。

### T6 供应链（关键变量：库存与交期对比，最强任务）
- **stage1**：核心元器件由单一供应商提供，交期 6 周，成本占比 30%，当前库存可支撑 4 周
  生产。分析主要矛盾，列出关键变量，写入 issues。
- **key_facts**：`单一供应商`、`6周`、`30%`、`4周`
- **stage2**：供应商所在地区突发风险，预估停产 8 周。给出应对决策与理由。
- **expected_decision**：必须双轨应对（现有库存 4 周 < 停产 8 周 < 替代交期需评估），
  不能只做"继续等供应商恢复"或"只找替代不管库存"。关键依据：4 周库存 vs 6 周交期
  对比（stage1 key）。

### T8 招聘排期（关键变量：人力与交付周期）
- **stage1**：3 人 6 周交付项目（含 A/B 双模块），给出排期方案与理由。分析主要矛盾，
  列出关键变量，写入 issues。
- **key_facts**：`3人`、`6周`、`A`、`B`
- **stage2**：B 模块核心工程师离职。团队已启动招聘，预计新工程师 3 周后到岗，培训期约
  2 周。给出调整后的排期与理由。
- **expected_decision**：交付周期需延长或重新分配人力（3+2=5 周损失 > 剩余时间预算），
  不能维持 6 周原排期。关键依据：6 周总周期 + A/B 双模块（stage1 key）。

## 6. 提示词（v2/ 目录，冻结）

- `prompt-s1.md`：阶段 1（分析 + 写 issues）。核心：具体问题具体分析 + 抓主要矛盾 +
  写 unresolved；**issues 必须包含决策所需的具体变量值（数值、约束、信号）**；允许
  `primary: null`；负禁则（空话词表沿用 V0）。
- `prompt-s2.md`：阶段 2（决策）。中性：基于可得信息给出决策与理由；若信息不足，说明
  缺什么、需要什么。P 组第一轮追加 P_TAIL（memory_reads 声明格式）。

## 7. 运行参数（冻结）

- 模型：ternary-bonsai-2-27b @ 127.0.0.1:8081（65536 ctx，服务端已起）
- temperature=0；max_tokens=8192（V2 输出规模小于 V1，无 reasoning 失控史；
  若出现截断，记录后升档，不静默）
- 通道：b+（模型输出声明块 → 脚本调真实 store；阶段 1 写、P 组读）
- DATA_DIR：`packages/.test-data/v2-memory`（每任务跑前清空）
- 运行：cwd=`packages/..`，
  `node --import tsx/esm bench/multi-agent/v2/run-v2.mjs [--only T1]`

## 8. 预注册的可证伪条件

- P 组"未发起取回"率 > 50% → memory_reads 协议对 27B 不可用（提示词问题或通道问题）。
- 三组决策质量全等 → 任务 key_facts 设计失效（阶段 2 不依赖阶段 1），任务需重设计。
- 传递完整性 < 80% 且 P < F → 协议价值为负，H-协作不成立，V2 结论为负。

## 9. 判定执行清单（V1 教训：判据执行清单化，逐条对照预注册原文）

1. 判定 P/N/F 三组前，先逐条对照本文件 §1 定义（信息通道内容、是否有读取提示）。
2. key_facts 命中用子串匹配（原文值），模型用同义词/换算表达时记"等价命中"并备注。
3. 决策质量判定先写"方向"，再写"key_facts 支撑"，两维分列，不混为一句。
4. 任何与 §2 判读规则冲突的结果，先查任务/通道问题，不临场改判据。
