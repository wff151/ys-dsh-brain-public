# 架构：三角 + 规则调度层
> 从项目内部 `DESIGN.md` 提炼的公开版。版本 1.0（2026-10-02）。
> 说明：这是**设计意图**，不是已验证的结论。V0/V1/V2 的实测未验证协作层的额外价值（详见 `conclusions.md`）。
## 1. 总体结构
三个 LLM 角色 + 一个规则调度层。**排期不是第四个 LLM agent**——降为规则调度器（不产生判断，只做账本与报警）。
```
                 ┌────────────────────┐
                 │       用户         │  ← 最终决策权
                 └─────────┬──────────┘
                           │ 主动建议 / 冲突上抛
                 ┌─────────▼──────────┐
                 │  战略 agent（LLM）  │  方向假设、指标趋势、转向预警
                 └─────────┬──────────┘
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
   │ 矛盾分析 agent│  │  规则调度层   │  │ 执行 agent    │
   │ (LLM) 主次判断 │→│ (非LLM) 账本  │→│ (LLM) 干活验证 │
   └──────────────┘  └──────────────┘  └──────────────┘
                          │ 报警/资源约束
                          ▼
                   共享黑板（public）
                   随身文档（portable）
```
## 2. 角色定义
### 2.1 战略 agent（LLM）
- **主动建议权**：可发起方向调整、预警、提议（不等待被问）。
- **最终决策权在用户**：战略 agent 是副驾驶，不是自动驾驶员。
- 不可逆操作、预算超限、伦理决策必须用户批准。
- 冲突规则：用户明确指令 > 战略 agent 提议；双方判断冲突时暂停并上抛；紧急情况可临时调整但需事后报告。
### 2.2 矛盾分析 agent（LLM）
- 职责：三层矛盾分类、输出优先级列表、转化条件。
- 三层分类（判据写死，可审计）：
| 层级 | 判据 | 处理 |
|---|---|---|
| 主要矛盾 | 不解决 → 验收标准无法达成 | 优先解决，当前轮必须动 |
| 次重要矛盾 | 不解决 → 验收能达成，但方向会偏或成本/风险上升 | 并行观察，排进近期 |
| 次要矛盾 | 不解决 → 验收达成、方向不偏，只影响效率/体验/可维护性 | 往后推，可登记不做 |
- 允许"无主要矛盾"出口：不强行选一个。
- 触发时机：阶段切换 + 主要矛盾标记解决 + 指标异常 + 外部约束变化。
### 2.3 执行 agent（LLM）
- 职责：按调度结果干活、验证、回写黑板。
- 随身文档记录：当前步骤、工具日志、试错记录、局部细节。
### 2.4 规则调度层（非 LLM）
- 职责：
  - 检查矛盾分析给的优先级是否违反资源约束（WIP 限制、时间空位、依赖未满足）
  - 违反则报警并回给矛盾分析（不自己改序）
  - 管理三类空位占用率
  - 登记每个任务的清理任务和未决问题
  - 输出资源账本
- 不做：不重新判断优先级、不覆盖矛盾分析排序、不决定方向。
## 3. 存储映射
| 用途 | 表 | 工具 | 归属 |
|---|---|---|---|
| 共享黑板 | public | 写 remember；读 search / listAllPublicMemories | 跨 session 全局可见 |
| 随身文档 | portable | 写 note；读 resume | session 隔离 |
### 3.1 黑板 = public，append-only 事件流
- 每次状态更新 = 一条新 public 记录，带 agent 标识（写入 source 或 tags）
- **版本 = `time`（ISO 8601 字典序=时间序，单调不降）**；`memory_id` 只作唯一标识
- **并发写 = append，天然无冲突**
- 读取：search（按 query 检索）+ listAllPublicMemories（全量折叠）
- **状态折叠**：黑板当前状态 = 按 agent 分组取最新字段（纯函数，放规则调度层）
### 3.2 随身文档 = portable
- 每个 agent 一个独立 session → portable 按 sessionId 天然归属
- `exchangeCount` 天然单调版本
- 无并发问题（单 agent 写自己的随身文档）
### 3.3 resume 的 onlyUnresolved 约束
`resume` 默认 `onlyUnresolved=true`，只看有 issues 的会话。写入规则：
- 矛盾清单 → 写 `unresolved`（issues）
- 方向假设 → 写 `unresolved`，或调度层读时传 `include_recent`
- 空位 / 尾巴 → 写 `unresolved`
- 已完成事项 → 不写 issues，写 `result`
## 4. 三类空位（规则调度层管理）
| 类型 | 用途 | 例子 |
|---|---|---|
| 时间空位 | 未执行任务、返工、意外 | 每轮留 20–30% 时间 |
| 功能空位 | 未开发功能、预留接口 | 接口占位、TODO 登记 |
| 清理空位 | 尾巴清理、回退、文档 | 每任务固定清理时间 |
管理规则：
1. 空位不能被填满（发现被填满要报警）
2. 空位要有主（谁负责、什么时候用、不用怎么办）
3. 功能空位要有最迟处理时间，否则变技术债
4. 尾巴清单和清理空位联动
## 5. 验收标准（每任务，含清理）
- 功能完成；测试通过；文档/日志更新；临时文件清理；回退脚本可用；未决问题登记
- 否则"完成"只是功能完成，尾巴越积越多
## 6. 落地顺序（设计意图）
- **V0**：单 agent + 结构化提示词 + 黑板（public 事件流）+ 随身文档（portable）
- **V1**：拆执行 + 矛盾分析，加规则调度层 + 黑板折叠函数
- **V2**：加战略 agent（主动建议权）
- **V3**：多 agent 通信、评测、人工在环
**实测结果**（详见 `conclusions.md`）：V0/V1/V2 三轮测试未检出协作层的额外增益——格式协议在多 agent 交接中传递完整（100%）但与"直接给全文"等价。这个架构**已实现的部分**（存储映射、事件流、折叠设计）可用，**未实现的部分**（真多 agent 拆分、战略 agent）随假设降级延后。
## 7. 存储验证要点（实测已验证）
以下 9 项在实现前已零模型验证：
1. `remember` 写结构化字段 ✅
2. `note` 按 agent 归属（sessionId 天然隔离）✅
3. 并发写冲突检测（方案规避：append-only）✅
4. 版本号原子更新（方案规避：public.time 单调）✅
5. domain+version 索引 ⚠️ 无索引（个人规模可接受）
6. resume 渲染完整性 ✅（M-001 修复后）
7. subagent 独立 sessionId ✅
8. portable 跨 session 读 ✅
9. public 的 `time` 单调性 ✅（`memory_id` 只作标识）
**"public store 跨 subagent 共享"** 是 V2 前置的关键验证项，未通过则整条路径走不通；实测通过（详见 `bench/multi-agent/UNRESOLVED.md`）。
## 8. 可证伪条件（设计期预注册）
- 随身文档与黑板冲突率高 → 双文档结构成本 > 收益
- 三层分类中"次要矛盾"占比长期 >70% → 分类退化为拖延借口
- 战略 agent 方向调整被用户否决率 >50% → 判断质量不足或权限边界不清
- 空位被填满率 >80% → 调度层没守住缓冲
- 尾巴清单增速 > 清理速度 → 验收标准执行不严
- 调度层冲突报警率 >30% → 资源约束前移到矛盾分析输入
## 9. 与实现的关系
本仓库的 `packages/dsh-memory`、`packages/dsh-conduct` 是这个架构的**部分实现**：
- `dsh-memory`：黑板（public 事件流）+ 随身文档（portable）+ resume/search 工具，是实现层
- `dsh-conduct`：提示词编排的载体，是注入层
- `dsh-brain-dispatch`、`dsh-brain-confinement`、`dsh-brain-bundle`：调度 / 准入 / 打包的骨架
完整四角色多 agent 编排**未实现**——V2 用 b+ 通道 + 手工跨 session 模拟交接；官方 subagent 编排能力只验证了"public store 跨 subagent 共享"一项（其余 7 项见 `bench/multi-agent/UNRESOLVED.md` U8）。
